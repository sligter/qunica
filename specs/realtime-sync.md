## 4. P0：WebSocket 多端同步

### 4.1 连接、实例与登录

- 统一使用服务器 origin：`https://qunica.example.com` 或 `https://<IP>[:port]`，第一版不支持路径前缀部署。
- 公网使用 HTTPS/WSS，IP 访问的证书必须匹配 IP 并被客户端信任；域名不是强制条件，关闭证书校验不能作为 IP 连接方案。loopback 开发允许 HTTP/WS。
- 增加无密钥信息的实例能力接口，返回稳定 `server_id`、协议版本、执行环境能力与构建版本。切换实例先清除旧连接、查询缓存、消息草稿绑定和游标，再建立新实例会话；不能把旧服务器令牌发往新地址。
- 桌面提供“本地实例 / 连接服务器”；远程模式不要求启动本地后端。Android 的服务器地址设置与登录已存在（见现状表），本轮改动在于把直连设为默认入口、补齐服务端撤销与实时通道；不要求扫码、桌面在线、Noise 或 VPS 中继。
- 旧配对记录不自动转换成远程服务器凭据，不静默删除配对数据；用户选择远程地址后重新认证。配对作为支持的连接方式保留，不以 VPS 直连替换或下线。
- 实时通道分两条链路，不能混用：直连实例（含 VPS）走 WSS；手机配对桌面的链路把原生加密 TCP 包成 Fetch 流（`frontend/src/lib/lanFetch.ts`，只允许 `https://qunica-lan.invalid` 这个哨兵 origin），浏览器 WebSocket API 无法骑在该通道上，但 `lanFetch` 已返回流式 Response，SSE 可用。因此 P0 为配对链路提供账号事件 SSE（提议 `GET /api/v2/account/events?cursor=`），与 WS 共用 `account_events`、快照、游标和 `resync_required` 语义；配对端命令走现有 HTTP 接口及同一 `command_receipts` 去重。配对端由此获得与直连相同的跨端发现能力，不需要原生 WS 桥。原生 WS 桥仅在 SSE 无法满足延迟或流量要求时重访。
- 配对设备接入同一服务端会话与授权层，每台手机获得独立 session，不能复用桌面的 session_id。旧配对令牌同样按 `session_upgrade_required` 处理，明确提示重新扫码或登录；撤销设备同时拒绝其后续请求并关闭现有 Noise/SSE 连接。配对身份校验和应用账号授权仍分别校验，不允许哨兵 origin 绕过认证。
- Web 使用同源资源和接口；桌面、Android 的 CORS、CSP 与 WS Origin 校验使用明确来源配置。不能把 CORS 检查等同于 WS 鉴权。

提议建立服务端设备会话 `auth_sessions`：新令牌携带 `session_id`，HTTP 和 WS 都检查未撤销状态。登录继续保持到主动退出，不增加按天过期或刷新令牌流程；退出当前设备、撤销设备必须使对应连接和后续请求失效，不影响其他设备。

不提供旧 JWT 换新会话的升级流程。不含 `session_id` 的旧令牌在 HTTP 与 WS 入口一律返回 401 及明确错误码（提议 `session_upgrade_required`），客户端清除旧令牌并提示重新登录；每台设备只需重新登录一次，之后保持持续登录。这样不需要持久化旧令牌消费记录，也没有重复兑换问题。客户端对该错误码的处理与存储清理必须有迁移测试；在 `auth_sessions` 上线前，不能宣称客户端退出已具备服务端撤销能力。

### 4.2 WS 握手与协议

路径：`GET /api/v2/realtime`，当前实现子协议 `qunica.realtime.v2`，同一 scope 的事件批量发送，v1 客户端须升级。使用现有 HTTP Bearer 认证取得一次性 ticket：`POST /api/v2/realtime/tickets`。ticket 绑定服务器、账号与会话，30 秒过期、只能消费一次；通过 WS 第一帧提交，不能把长期令牌放入 URL 或日志。连接 5 秒内未认证即关闭，认证前不允许订阅和命令。

消息分为 `hello`、`authenticate`、`subscribe`、`unsubscribe`、`command`、`command_result`、`events`（内含原 `event` 形状）、`ack`、`resync_required` 和应用层 `ping/pong`。浏览器无需手动发送 RFC 控制帧。协议主版本不兼容时返回明确错误，不能无限重连。

命令示例：

```json
{
  "type": "command",
  "request_id": "9dd85e71-230f-4b44-b962-dcc192583aaf",
  "name": "message.send",
  "target": { "conversation_id": "group-1", "thread_id": "task-1" },
  "payload": { "content": "检查这次修改", "attachments": [] }
}
```

接收成功响应返回 `request_id`、`status: accepted`、`job_id`、`turn_id` 与 `stream_id`；这些标识在接收事务内确定。`accepted` 只表示已持久接收，不表示执行或交付已完成。客户端收到响应前断线，可用相同 request_id 查询或重试。job 的占用按 owner + thread 约束，同群不同任务线程可以并行；同线程审批、取消收尾与重启恢复仍按序处理，自动任务的发生项及共享电脑另有资源约束（见 [自动触发队列合同](automations.md#64-队列竞争与恢复)）。

### 4.3 两类订阅与事件

| 订阅 | 覆盖范围 | 游标与数据 |
| --- | --- | --- |
| `account` | 当前账号的群/私聊/任务变化、成员与配置更新、消息摘要、运行状态、审批待办、电脑和自动任务状态 | 持久 `account_seq`，用于发现其他设备发起的操作；不重复存储每个 token。 |
| `run:<stream_id>` | 当前查看或明确关注的运行，其 token、reasoning、工具、待办与调度细节 | 保留现有 `stream_id + seq` 及运行事件类型；可独立重放。 |

账号事件中的运行开始、消息变化和终止摘要必须足以让未订阅 token 的设备发现新工作并更新列表；打开会话时再取快照、订阅细节。不得依靠当前页面或发起设备通知其他设备。

事件外层包含 `event_id`、`scope`、`cursor`、`occurred_at`、资源标识和可用时的 `resource_version`。账号序号在线上协议中使用十进制字符串；顺序由服务端序号决定，不使用客户端时钟。运行事件原有标识保持稳定，外层游标不得让客户端混用账号与运行序号。

每次订阅、补拉和命令均从认证主体校验资源归属；客户端传入的 owner、group 或 stream 标识不构成授权。第一版按现有账号所有权模型广播，不新增跨账号共享房间。

### 4.4 快照、重连与去重

1. 首次连接或应用重新启动，获取账号快照：群与任务摘要、活动运行、待审批事项、资源版本和账号 high watermark；不返回密钥和完整历史。
2. 快照数据与 watermark 必须来自同一数据库读事务。客户端从该 watermark 订阅，服务端先补齐之后的事件，再连续跟随数据库增量；进程广播遗漏不能产生缺口。
3. 查看线程时，取得该线程的分页消息、在途输出、对应运行游标和审批状态，再从该运行游标追增量。历史归并按 message id upsert、按服务端消息序号排序。
4. 短暂断线保留内存状态和已应用游标，重连后补拉；只有成功应用事件才能推进 cursor/ack。异常中断不能自动重新发送旧的执行请求。
5. 第一版不单独持久化游标：应用重启重新获取快照。若未来持久化本地消息缓存，缓存与游标必须原子保存，避免“有游标、无状态”。
6. 服务端明确区分游标过期、实例不匹配、未授权和暂时不可用。过期返回 `resync_required`，客户端重取快照，不从零盲目重放所有工具输出。
7. 账号事件建议保留最近 7 天且最多 100,000 条/账号；已结束运行的事件采用可配置保留期。活动运行及待审批的恢复材料不得被普通清理删除，正式消息和审计记录的保留独立管理。

客户端切换账号/服务器必须使旧连接回调失效，清空对应缓存；旧任务的迟到事件不得写入新任务。消息删除、清空、任务归档和审批变化也必须产生领域事件。账号摘要与运行细节跨订阅到达时，以正式消息版本及终态为准；终态之后的迟到 token 不得复活已结束或已删除的消息。

### 4.5 命令接收与跨端竞争

- 首批 WS 命令：`message.send`、`turn.cancel`、`thread.resume`、`approval.resolve`。资源 CRUD、历史、文件上传下载继续走 HTTP，并产生相同账号事件。
- `command_receipts` 对 `(owner_id, request_id)` 设置唯一约束，记录命令类型、完整目标、规范化载荷摘要与响应。同 ID 同内容返回原响应，不再创建运行；同 ID 不同目标或内容返回 `idempotency_conflict`。
- 归档、清空或删除任务不释放其 request_id；删除完整响应后仍保留最小去重 tombstone，旧命令只能返回已删除/已结束状态，不能重新执行。
- receipt、用户消息、运行/作业接收记录和相关领域事件原子提交；双连接同时发送时依靠数据库唯一约束裁决。已有 `client_request_id` 兼容映射到同一去重入口，不能另建一套弱去重。
- 运行启动由服务端作业循环接管。关闭连接、页面切换和客户端背压不会停止运行；停止必须显式命名 turn，旧停止请求不能取消新回合。
- 待审批请求需要可持久恢复的实体，绑定 thread、tool_call、不可变动作载荷摘要和版本。`approval.resolve` 以 pending 状态及 expected_version 原子裁决；多端同时同意/拒绝只允许一个结果生效，其他设备收到当前决定。过期审批不得执行新载荷。现有恢复路径经 `POST /api/v2/threads/:id/resume` 从消息历史重建待答调用，可作为迁移起点；但 `recover_incomplete_turns` 现在会把等待中的回合判为重启失败，本轮必须先把它改成“重启后仍可恢复的等待”，否则 VPS 重启后待审批直接丢失。
- 已有记住审批的权限仍只在原 thread/rule 范围生效，不能扩展成跨群或跨设备的全局授权。
- 走 HTTP 的写入（群与任务 CRUD、文件操作、归档、清空、审批答完）必须在同一事务里发出同类账号事件，否则 WS 只覆盖聊天，列表仍靠轮询刷新。现有轮询只覆盖局部：消息在活动回合时 2 秒、文件与 Git 10 秒，群与任务列表既无轮询也无窗口聚焦刷新，新运行在未打开的端上等于不可见。M1b 后这些轮询降级为事件缺失时的兜底，验收不以轮询作为实时性来源。
- 内部命令接收可做到一次入队；网络或第三方工具的实际外部副作用不承诺全局 exactly-once。结果不确定时先观察并核实，不能自动重放。

### 4.6 背压、心跳、终端与通知

主连接的队列按字节和消息数双重限额，建议起点为 4 MiB / 2,048 条；超限断开慢客户端，后续按游标恢复，不阻塞 runtime，不静默丢弃持久事件。token 可批量传输但必须保留序号范围和原内容；应用层每 20 秒探测，60 秒无响应后断开，以带抖动指数退避重连。参数需通过弱网测试确认。

服务器终端使用独立 WS 通道复用 ticket 鉴权，隔离 PTY 高流量。终端输出用现有环形缓存/序号恢复；超出缓存明确提示需要重新绘制。键盘输入默认不自动重发，避免重复执行命令；输入、resize 与关闭均校验终端归属。不能把终端字节无限写入账号事件日志。桌面本机 PTY 的本地适配无需为远程协议强制替换。终端会话本身是进程内状态，服务重启后消失，与“回放窗口不足”属两种错误，客户端要分别提示重新打开会话或重新绘制。同一会话被多个客户端打开时，输入需短期租约：只有持租约的端能写入与 resize，其余只读观察并提示正在被其他设备操作；租约随连接断开或显式交还释放，旧租约 generation 不能再输入。

前台客户端通过账号事件生成结果通知，按事件 ID 去重。Android 被系统挂起后不承诺 WS 常驻或系统推送；回到前台必须补齐。离线发送队列和系统 Push 不属于 P0。

### 4.7 迁移要求

先建立与传输无关的命令、事件和快照服务，再接 WS，再迁移直连模式的 Web/桌面/Android，最后停止直连客户端使用聊天与远程终端 SSE。配对方式继续使用 SSE 适配器（运行流与账号事件流），仍调用同一命令、授权、审批和事件恢复服务；不能因为第二条订阅或传输切换而再启动 Agent。

实例能力接口明确暴露连接方式及协议支持范围；不满足该连接方式最低协议的客户端收到升级提示。迁移结束的门槛是直连三端验收与配对兼容回归完成；不得把仍服务配对的 SSE 接口列为废弃并删除。允许维护两种传输适配，不维护两套执行、权限或恢复规则。

### P0 必须通过

1. 桌面发消息，Web 与 Android 在未发起请求、未打开该群时发现新运行；打开后输出与服务端一致。
2. 手机审批后桌面同步；两端同时做相反决定只生效一次，执行载荷与批准载荷一致。
3. 同 request_id 并发/断线重试只产生一条用户消息、一个 job 和一个 turn；不同载荷被拒绝。
4. 快照获取与订阅之间插入消息/审批/新任务，最终无缺失、重复或顺序漂移。
5. 断网、切群、切任务、后台恢复、重启客户端、游标过期均能恢复；旧请求不能重新发起执行。
6. 全部客户端断开后，服务端任务继续并保留结果；慢客户端超限不阻塞其他设备或 Runtime。
7. 退出/撤销设备切断该设备 HTTP 与 WS；另一设备继续工作。不含 session_id 的旧令牌在 HTTP 与 WS 均返回 `session_upgrade_required`，客户端清除并引导重新登录。
8. 错账号、错实例和错资源订阅被拒绝；切服务器后旧回调、缓存和令牌不污染新实例。
9. 域名及受信任 IP 的 HTTPS/WSS 直连通过；连接中不包含 Noise、frp 或桌面转发依赖。
10. 终端断线后的输入不会自动重发；输出超出恢复窗口给出明确提示。
11. 同一终端会话在两个客户端同时打开时，只有持输入租约的一端能写入；服务器重启后客户端区分“会话已消失”与“回放不足”。
12. 审批等待期间重启服务，重启后待答请求仍可在任一客户端答完并继续执行，不因重启被判失败。
13. 保留的 Noise 配对方式完成独立会话、收发、SSE 恢复、审批、文件与终端兼容回归；配对端的 HTTP 写入能被直连端账号事件观察；直连端发起的运行与审批也能经账号事件 SSE 被配对端发现，断线后按同一游标补齐。设备撤销切断配对请求/流。

P0 性能测量基线：无 Agent/模型推理负载、2 vCPU / 4 GiB 服务端、3 个前台客户端、网络 RTT 不高于 100 ms 时，已提交消息/状态跨端可见延迟目标 p95 ≤ 1 秒；弱网重连恢复单独记录。正确性门槛不能被平均延迟掩盖，未实测不得标记通过。同时记录全局 `write_lock` 等待与事件落库耗时：写锁等待 p95 超过 100 ms 时先修写入路径，不能把 SQLite 单写者的排队算作网络延迟。
