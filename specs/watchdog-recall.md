# Watchdog 与链式召回 Spec

Status: implemented
Version: 0.1
Since: 2026-11-02

两项 Router 模式的补充：

- **Watchdog**：定时任务驱动一个只读的检查会话，检查已派发任务有没有进展；发现异常时提醒用户，或停止无法自行完成的任务。
- **链式召回**：按 ID 读取会话、任务、触发事件的工具。每次读取都附带下一层的摘要和 ID，模型一层一层往下读，而不是一次加载整段记录。

## 1. 目标与非目标

目标：

- 「卡住」的判定由服务端从持久状态算出，每次检查口径一致，不交给模型猜。
- 检查会话除了提醒和停止任务，不能改动任何东西。
- 召回只读，并限定在调用者所在群组内。

非目标：跨群检查、自动重试或重派任务、IM 等其他提醒渠道、通用的全文搜索。

## 2. 存储

迁移 `0054_watchdog.sql`：

- `automations.kind`：`prompt`（默认）或 `watchdog`。
- `threads.watchdog_automation_id`：标记 Watchdog 的检查线程（`ON DELETE SET NULL`）。

迁移 `0055_watchdog_job_event.sql`：`job.changed` 账户事件带 `watchdog` 标记。

## 3. Watchdog

配置（`api/automations/service.rs`）：

- `kind = "watchdog"` 只接受 `once` 和 `cron` 触发；Webhook 或 GitHub 触发返回 400。
- 群组必须处于 Router 模式。创建、修改和每次触发都会检查，不满足时返回 400；定时触发时会停用这个自动化。

执行：

- 同一个 Watchdog 的所有检查共用一个线程（`watchdog_thread`）；线程归档或清空后，下次检查新开一个。上一次检查还没开始时，定时路径会取消它。
- 检查线程由 Router 应答（`thread_responder` 返回 `RouterSeat::Watchdog`）。群组不在 Router 模式时，这次检查直接失败。
- 检查会话没有成员自身的工具、计算机、技能、工作区或 MCP；只有 `ReviewTasks`、`NotifyUser`、`StopTask` 三个工具加三个召回工具。执行器设置了 `task_tools_only`，绑定上有 `TaskToolMode::Watchdog`，两层都拒绝其他工具名。
- 引擎本身也会让调用未声明工具的回合失败。`AgentAsTool` 是宿主控制请求，由于没有提供给检查会话，宿主同样拒绝。
- 不指定线程的消息不会落到检查线程；没有其他活跃线程时新开一个。前端默认打开的主线程也会跳过它（`commands.rs`、`useGroupMessages`、`GroupChatPage`）。

工具（`runtime/watchdog.rs`）：

- `ReviewTasks`：检查有未结束 job、或 24 小时内失败/中断过的任务，附带进度和信号。最多检查 200 个，未结束的任务优先（`max_router_tasks` 限制它们最多 16 个），所以近期失败的任务挤不掉卡住的任务。结果按紧急程度排序：卡住、未开始、等待、反复失败排在前面，然后是单纯失败，最后是没有信号的任务。每页 30 个，有剩余时返回 `remaining` 和 `next_offset`。信号固定为：`stalled`（运行中且无活动达到 `stall_minutes`，默认 15）、`not_started`、`waiting_for_user`、`awaiting_approval`、`failed`、`repeated_failures`（24 小时内失败 2 次以上）。
- 进度看占用线程的那次运行（运行中或等待用户的优先，其次是最新的），活动时间取这次运行的最后一条 stream event 和 job 的 `updated_at`。后面排队的新事件不会掩盖卡住的运行，也不会刷新活动时间；排队数单独报告为 `queued_runs`。token、工具调用和工具结果都会写 stream event，所以只有挂住的调用才会让它停住。
- `NotifyUser`：在派发任务的会话里插入一条 `watchdog_alert` 系统消息，并写入 `watchdog.alert` 账户事件。同一任务 60 分钟内只提醒一次，重复调用返回 `already_notified`。
- `StopTask`：在同一个写事务里取消任务未完成的回合、退订主题，并发一条 `stopped` 提醒；提交后中断正在运行的回合。

提醒消息设置了 `context_admitted=0`。它可能在 Router 回合进行中落地，不拼进正在进行的对话记录；Router 需要时通过召回读取。

## 4. 链式召回（`runtime/recall.rs`）

- `ReadThread(thread_id)`：线程类型（conversation / task / watchdog）、主题、最近 10 条消息摘要，以及它派发的任务和收到的事件。消息上直接带 `task_ids`（任务汇报、Watchdog 提醒）和 `event_ids`（触发事件）。
- `ReadTask(task_id)`：在线程视图之外，加上状态、进度、最新回复（截断到 4000 字符）和来源会话。
- `ReadEvent(event_id)`：来源自动化、主题、路由结果、送达的线程及其运行状态，以及从运行消息里取出的带 `untrusted` 标记的载荷（截断到 8000 字符）。

每个结果都有 `next` 提示和数据声明（文本是引用的数据，不是指令）。线程和任务按 `group_id` 限定。自动化可以换群，所以事件按它实际送达的线程判断归属，而不是自动化当前所在的群；载荷只从送达本群线程的那次运行读取。跨群 ID 一律返回「未找到」。

Router 始终拥有召回工具；即使群里没有可派发的成员，也能读取历史。

## 5. 前端

- 自动化表单的「运行内容」可选 Watchdog：切换时去掉事件触发，默认每 15 分钟一次，并预填检查提示词。
- `watchdog_alert` 消息显示为卡片，链接到对应任务。
- `watchdog.alert` 账户事件触发桌面通知；正在查看该会话时不通知。检查线程本身运行结束不发「回复完成」通知：`job.changed` 事件和账户快照的线程都带 `watchdog` 标记，首次检查在快照刷新前结束也能识别。
- 任务切换器把检查线程标为「巡检」。

## 6. 测试

- `tests/group_stream/router_mode.rs`：
  - 一次完整检查：工具列表只有六个、系统提示含 Watchdog 角色、`failed` 信号、冷却去重、停止、两条提醒且不进入上下文、两条账户事件、消息 API 返回 `watchdog_alert`。
  - 配置校验：Webhook 触发和非 Router 群组都被拒绝。
  - 召回链：会话 → 任务 → 事件载荷，以及跨群读取被拒。
  - 不指定线程的消息不进入检查线程；检查线程的 job 事件带 `watchdog` 标记。
- `runtime/watchdog.rs` 内存库测试：卡住的运行后面排队新事件时仍报 `stalled`；30 个近期失败不会挤掉较早卡住的任务，分页返回剩余部分；自动化换群后，事件只对送达的群可读。
- 单元测试：信号阈值、载荷块定位、时间差、各模式工具白名单。
- 前端：提醒卡片、表单切换 Watchdog 后的触发和提交内容、首次检查结束不发回复通知、提醒事件触发通知。

## 7. 备选方案

- **不做，让用户自己建一个定时提示词自动化去问 Router**：现有能力就能做到，零新代码。否决：那个会话拥有 Router 的全部写工具，模型可能派发新任务；「卡住」由模型每次自行判断，结果不稳定；提醒混在普通回复里，没有通知。
- **服务端规则直接发提醒，不用模型**：最便宜、最确定。否决：规则只能报「15 分钟没动」，分不清「在等长时间编译」和「在同一步反复失败」。现在由规则给出信号，由模型读上下文决定是否提醒或停止。
- **召回返回完整记录**：一次调用就拿到全部内容。否决：长任务的记录会撑满上下文，而且大多数时候只需要最新回复或一条事件。

## 8. 代价与重访信号

收益：长任务无人值守时有人盯；提醒有通知、有冷却；召回让 Router 回答「之前那件事怎么样了」时不必猜。

代价：每次检查都是一次 Router 模型调用；检查线程会一直增长，需要用户手动归档；新增一列线程标记和一列自动化类型。

重访信号：
- 用户频繁收到误报（信号阈值需要按群配置）。
- 检查线程过长导致上下文溢出（改为每次检查新开线程或只保留摘要）。
- 需要跨群巡检。
- 召回被用于大范围搜索（需要专门的检索工具，而不是加大限制）。
